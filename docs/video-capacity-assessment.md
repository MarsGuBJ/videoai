# 视频显示与服务器承载能力评估报告

评估日期：2026-07-07  
评估对象：视频查询 MCP / VideoAI 当前部署环境  
服务器：`zrpgs`，局域网地址 `192.168.11.194`

## 1. 每一路 1080p 视频最高带宽要求

本次用现场 1080p H.264 视频流和录像样本做了带宽测量：

| 样本 | 分辨率 / 帧率 | 测得码率 |
| --- | --- | ---: |
| `rtsp://192.168.11.198:5504/Streaming/Channels/101` | 1920x1080 / 25fps | 约 4.85 Mbps |
| `demo-recording-601.ps` | 1920x1080 / 25fps | 约 5.08 Mbps |
| `/tmp/hik-test.flv` | 1920x1080 / 25fps | 约 5.40 Mbps |

结论：

- 当前现场一路 1080p 主码流的实际视频码率约为 `5 Mbps`。
- 规划容量时建议按 `6-8 Mbps / 路 / 方向` 估算，包含协议开销、码率波动和安全余量。
- 如果服务器同一张网卡同时从摄像头取流并向浏览器分发，同一路视频会同时占用入方向和出方向带宽，按 `12-16 Mbps / 路` 估算更稳妥。

## 2. ZLMediaKit 实例可负载的视频路数

当前主要使用的 ZLMediaKit 实例为 `zlmmediakit-main-1`：

- HTTP：宿主机 `81 -> 容器 80`
- RTMP：宿主机 `1934 -> 容器 1935`
- RTSP：宿主机 `8554 -> 容器 554`
- WebRTC：宿主机 `8000`
- 当前配置开启了 HLS、RTMP、RTSP；无观看者的流会在约 20 秒后自动关闭。

使用 1080p H.264 录像样本进行 RTMP 推流和 HTTP-FLV 拉流压测，结果如下：

| 并发规模 | 压测方式 | 结果 | ZLMediaKit CPU |
| --- | --- | --- | ---: |
| 16 路 | 16 路推流 + 16 路 FLV 拉流 | 稳定 | 约 11-19% |
| 32 路 | 32 路推流 + 32 路 FLV 拉流 | 稳定 | 约 17-30% |
| 64 路 | 64 路推流 + 64 路 FLV 拉流 | 稳定 | 约 42-47% |

结论：

- ZLMediaKit 进程本身可以稳定承载 `64 路 1080p 输入 + 64 路播放输出`，CPU 仍低于 50%。
- 按 CPU 线性估算，ZLMediaKit 进程瓶颈大约会出现在 `100-120 路` 1080p 输入输出配对附近。
- 但当前服务器生产环境使用的是 `1Gbps` 局域网网卡，实际可用路数会先受网络限制，不应只按 ZLMediaKit CPU 估算。
- 当前网络条件下，建议生产并发控制在 `50 路以内` 1080p 实时显示；如果需要更高并发，应优先升级到 10GbE 或降低码率、使用子码流。

## 3. 当前服务器所在局域网带宽情况

服务器主用网卡为 `enp60s0f0np0`：

- 链路速率：`1000Mb/s`
- 双工模式：Full Duplex
- 当前链路状态：Link detected
- 10 秒采样流量：入方向约 `47.87 Mbps`，出方向约 `57.47 Mbps`
- 网卡错误包：RX/TX errors 为 0
- RX dropped：累计约 `1,358,835`，该值是 59 天运行期的累计值，需要持续观察是否仍在增长。

结论：

- 当前局域网链路不是 10GbE，而是 `1GbE`。
- 采样时网络没有被打满，当前实时流量约占链路的 5%-6%。
- 按稳定运行保守阈值 `700-800 Mbps` 计算，若一路 1080p 按 `6-8 Mbps` 输出，理论可承载约 `87-133` 路单向播放输出。
- 如果每一路都同时从摄像头入流并向浏览器出流，应按 `12-16 Mbps / 路` 计算，生产上更合理的上限约为 `44-66 路`。

## 4. Windows 浏览器在不少于 20fps 时可显示多少路视频

当前浏览器播放链路的关键限制不在 Windows 浏览器本身，而在服务端输出方式：

- 当前后端 MJPEG 接口 `/api/streams/{app}/{name}.mjpeg` 会为每个浏览器请求启动一个 `ffmpeg`。
- 该 `ffmpeg` 固定使用 `-vf fps=8,scale=960:-2`。
- 因此当前 MJPEG 播放链路最高只有 `8fps`，无法达到 `20fps`。

结论：

- 在当前 MJPEG 链路不改造的情况下，Windows 浏览器能显示不少于 20fps 的视频路数是 `0 路`。
- 如果改为 H.264 的 HTTP-FLV / HLS / WebRTC 播放，并让浏览器走硬件解码，按普通办公 Windows 终端保守估计，单屏稳定显示 `9-16 路 1080p >=20fps` 比较现实。
- 如果使用 720p 子码流或降低码率，可进一步提升同屏路数。
- 最终浏览器显示上限需要在目标 Windows 机器上实测，因为 CPU、GPU、浏览器硬件解码状态、屏幕布局和渲染框架都会影响结果。

## 5. 当前视频不顺畅原因排序

1. **当前 MJPEG 链路被固定限制为 8fps。**  
   服务端转码命令固定使用 `fps=8`，所以前端无论性能如何，都无法达到 20fps。

2. **每个浏览器视频窗口都会启动独立 ffmpeg 转码。**  
   当前是按请求拉流、转码、输出 MJPEG。多个用户或多个宫格观看同一路摄像头时，会产生重复 `ffmpeg` 进程，CPU 成本高。

3. **没有优先使用 ZLMediaKit 做统一取流和 H.264 分发。**  
   ZLMediaKit 压测显示其转发能力明显强于当前逐请求 MJPEG 转码模式。当前不顺畅主要不是 ZLMediaKit 扛不住，而是播放链路没有充分利用它。

4. **浏览器解码 MJPEG 的效率低于 H.264 硬解。**  
   MJPEG 是连续 JPEG 图片，带宽和 CPU 开销都偏高；H.264 通过 FLV/HLS/WebRTC 播放更适合多路实时视频。

5. **服务器当前只有 1GbE 局域网链路。**  
   当前流量未打满，但多路 1080p 同时入流和出流时，1GbE 会比服务器 CPU、内存更早成为系统上限。

6. **部分视频源本身存在质量或稳定性差异。**  
   现场存在 720p、10fps 的源，也观察到部分 RTSP 源返回异常。源端不稳定会直接表现为卡顿、黑屏或帧率不足。

7. **ZLMediaKit 无观看者自动关闭流。**  
   当前 `streamNoneReaderDelayMS` 约为 20 秒。该配置不是主要卡顿原因，但会影响压测、预热和诊断时对“流是否存在”的判断。

## 建议

1. 将浏览器实时播放链路从 MJPEG 优先切换到 H.264 HTTP-FLV、HLS 或 WebRTC。
2. 取消当前实时显示路径中的 `fps=8` 限制，目标至少按 `20-25fps` 输出。
3. 同一路摄像头只由服务端统一拉取一次，统一推入 ZLMediaKit，再由 ZLMediaKit 分发给多个浏览器。
4. 宫格预览优先使用子码流或低码率流，点开单路大画面时再切主码流。
5. 若目标是长期稳定显示超过 50 路 1080p，应升级服务器局域网到 10GbE，或拆分多台流媒体服务器。
6. 对 `enp60s0f0np0` 的 RX dropped 做持续监控，确认是否仍在增长。
